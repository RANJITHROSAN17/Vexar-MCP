# Product review — 0.2.2 (2026-10)

An evidence-based review of Vexar-MCP against the MCP specification, the official MCP security
guidance, and production-readiness expectations. Every claim below was produced by running a
command or reading the cited file; where a check could not be run, it says so.

**Verdict: READY** for the release described here, **with two accepted non-blocking risks** and
five documented deferrals (§7).

---

## 1. Executive assessment

### What this product is, and what it is not

Vexar-MCP is a **client-side analyzer**. It is not an MCP server and does not serve tools to a
model. That single fact decides most of this review:

| Question | Answer |
| :--- | :--- |
| Does it expose MCP tools? | **No.** There is no FastMCP/SDK server in `src/`. |
| Does it accept tool calls from a model? | **No.** |
| Does it act as an MCP *client*? | **Yes** — `audit-server` initiates `initialize` / `server/discover` against a server you name, over stdio. |

So the largest block of requirements in a generic "secure MCP product" checklist — inbound
authentication, OAuth, RBAC, rate limiting, HITL approval for destructive actions, sandboxed
tool execution, DDoS protection, health probes — **do not apply to this architecture**. They
would apply if the project shipped a server (see [roadmap RM-032](#7-deferred-work-and-accepted-risks)). Marking
them "N/A" is the honest classification; inventing equivalence would be the dishonest one.

What *does* apply, and is where this product's real risk lives:

> Vexar-MCP consumes untrusted input — someone else's source code, someone else's JSON
> manifest, and tool names served by a possibly hostile remote server — and renders it into
> reports a human reads and CI obeys.

### The two findings that mattered

**F-01 (High, fixed).** The client implemented only the `initialize` handshake. The current
protocol revision, `2026-07-28`, **removed** the handshake: version negotiation is per-request
via `_meta`, with a mandatory `server/discover` RPC. Consequence: *any server built on the
current revision could not be audited at all*, and the failure surfaced as
`server rejected 'initialize'` — which reads as the server's fault. For a tool whose entire
purpose is auditing MCP servers, that is a product-defining defect.

**F-02 (Medium, fixed).** No sanitization layer between untrusted text and output sinks. A tool
name or description could carry ANSI escape sequences into a terminal and a CI log, or open a
Markdown code fence/heading inside a PR comment. Not code execution; **content spoofing** — a
hostile input could make a report say something the scanner never found. For a security tool,
the report is the product.

The rest of the audit found the product in better shape than expected: HTML escaping, secret
redaction, subprocess handling, resource bounds and the "never execute scanned code" claim all
verified as genuinely implemented rather than merely documented.

## 4. Threat model (abridged)

Request path for the only inbound attack surface:

```
analyzed file / manifest / remote server response
   → loader (ast / json / lexical)      [untrusted]
   → rules                              
   → ScanReport                       
   → reporter → terminal | markdown | html | sarif | json | CI annotations
```

| ID | Threat | Control | Residual |
| :--- | :--- | :--- | :--- |
| T-01 | Malicious scanned code executes during analysis | `ast.parse` only; no import, no exec, no `eval`; subprocess only to launch a server the *user* names | none known |
| T-02 | Content spoofing via control chars / Markdown / CI commands | `sanitize.py` at every sink; 29 tests | exotic Unicode homoglyphs are out of scope |
| T-03 | Secret values leak into reports | `SecretLiteral` stores pattern/target only, never the value | **PASS by design** |
| T-04 | HTML report injects markup / script | `html.escape` at every interpolation | none known |
| T-05 | Hostile server floods the client | 8 MiB cap, 50 pages, deadline, process-group kill | none known |
| T-06 | Out-of-tree file read via symlink | symlinked **directories** are not followed; symlinked **files** are read | **F-05, accepted** |
| T-07 | Parser crash on malformed input degrades to a false "clean" | `ParseIssue` + withheld score + exit `3` | none known |
| T-08 | Supply chain | 0 runtime deps on 3.11+; pinned dev extras; secret + dependency scanning in CI | not SBOM-signed |

## 7. Deferred work and accepted risks

| Item | Why deferred | Where tracked |
| :--- | :--- | :--- |
| Symlinked files resolving outside the scan root are read (F-05) | Content is never echoed and parse failures carry no file text, so exposure is limited to "a report mentions a path". A `--no-follow-symlinks` default would break legitimate monorepo layouts, and that trade-off deserves its own change. | RM-033 |
| Streaming HTTP transport for auditing remote servers | Requires an HTTP client, origin/auth handling and its own threat model; deliberately out of scope for a stdio-first tool. | RM-032 |
| SBOM + signed releases | No distributor requires it yet; `pypa` provenance is available once publishing works. | RM-023 |
| Token-estimator accuracy benchmark | Claim exists in a docstring, measurement does not. | RM-029 |
| Newer TS parser / unresolved-construct detection | Quality improvements, not security. | RM-027, RM-028 |

**Accepted non-blocking risks**

1. **F-05** — documented above, with the reasoning for not changing the default.
2. **No third-party server has been audited in CI.** The fixtures are ours; they prove the
   client's behaviour, not the ecosystem's variety. First real-world target is tracked in
   RM-031's follow-up and the distribution checklist in
   [`first-impression.md`](first-impression.md).
